# LumaRoom 0.20.0 — QC and Feature-Gap Report

Date: 25 October 2026  
Test target: current working tree, including the seven pre-existing modified Kotlin files  
Device: Pixel_10a Android Emulator (Android 17/API 37 preview, x86_64, 16 KB page-size environment)

## Executive summary

The core image pipeline is in good shape: debug and release APKs build, all 28 JVM tests pass, and all 28 connected-device tests pass. Gallery import, library display, editor launch, a live Exposure adjustment, undo, and return to Library were smoke-tested without a crash.

The app is not release-ready yet. The most important issues are:

1. Google Play submission is blocked because the app targets API 35; new apps and updates have required API 36 since 31 August 2026.
2. The in-app privacy statement says photos never leave the device, but Android Auto Backup is explicitly enabled and fallback imports are stored under `filesDir`, which Android backs up by default unless excluded.
3. A 16 KB compatibility warning blocks the first launch on the test emulator because packaged x86_64 native libraries are not 16 KB compatible.
4. Undoing an edit all the way back to the original still leaves the photo marked as Edited.
5. The newly added elliptical Lens Blur is not fully remapped for rotation/geometry during export, so preview and export can disagree.

## Bugs and risks

### LR-QA-001 — Google Play submission target is obsolete

- Severity: **Blocker**
- Type: Release/compliance
- Evidence: `app/build.gradle.kts:17` sets `targetSdk = 35`.
- Expected: New app and app-update submissions should target API 36 or later.
- Actual: Google Play has required API 36 for new apps and updates since 31 August 2026 (an extension, if granted, only runs through 1 November 2026).
- Fix: Move `compileSdk` and `targetSdk` to 36, review Android 16 behavior changes, and rerun the full test matrix.
- Source: https://support.google.com/googleplay/android-developer/answer/11926878

### LR-QA-002 — “Photos never leave the device” conflicts with Auto Backup

- Severity: **High**
- Type: Privacy/data handling
- Evidence:
  - `app/src/main/AndroidManifest.xml:8` sets `android:allowBackup="true"`.
  - `MainActivity.kt:357-362` copies photos whose URI grant cannot be retained into `context.filesDir/imports`.
  - The catalog database and SharedPreferences also use default backed-up locations.
  - The Settings screen states: “photos never leave the device.”
- Expected: Either imported photos and catalog data are excluded from cloud backup, or the privacy statement accurately discloses backup behavior.
- Actual: Android Auto Backup includes almost all files under `filesDir`, databases, and SharedPreferences by default. Backup can upload this data to the user's Google account.
- Fix: Add Android 12+ `dataExtractionRules` and legacy `fullBackupContent` exclusions (at minimum `files/imports`, the catalog, and sensitive preferences), or set `allowBackup=false`; then update the privacy copy.
- Source: https://developer.android.com/identity/data/autobackup

### LR-QA-003 — First launch is blocked by a 16 KB compatibility warning

- Severity: **High for QA/debug; release risk requires ARM64 verification**
- Type: Platform compatibility
- Reproduction:
  1. Install the debug APK on the Android 17/API 37 16 KB emulator.
  2. Launch LumaRoom.
  3. Android shows a blocking “Android App Compatibility” dialog.
- Actual warning names:
  - `lib/x86_64/libandroidx.graphics.path.so`
  - `lib/x86_64/libtensorflowlite_jni.so`
- Additional evidence: Lint reports `litert:1.0.1`'s x86_64 `libtensorflowlite_jni.so` as not 16 KB aligned. The release build also reports that it cannot strip `libandroidx.graphics.path.so` and `libtensorflowlite_jni.so`.
- Scope note: The release APK is ARM64-only, and `zipalign -c -P 16` passes. ELF LOAD-segment alignment of the ARM64 libraries still needs explicit verification on a 16 KB ARM64 device; do not assume the debug-only warning proves the ARM64 APK is broken.
- Fix: Upgrade LiteRT and relevant AndroidX dependencies to versions with 16 KB-compatible native binaries, then test the release artifact on a 16 KB ARM64 image/device.
- Source: https://developer.android.com/guide/practices/page-sizes

### LR-QA-004 — Undo-to-original still marks the photo as edited

- Severity: **Medium**
- Type: Library state/persistence
- Reproduction:
  1. Import a photo.
  2. Move Exposure from 0.00 to +2.04.
  3. Wait for autosave.
  4. Tap Undo so Exposure returns to 0.00.
  5. Return to Library.
  6. Observe the blue Edited badge and inclusion in the Edited filter.
- Expected: A recipe identical to the original/default state should remove the edit record and Edited marker.
- Actual: `touched` becomes permanently true after the first change (`MainActivity.kt:739-743`), `saveEdit` always upserts a recipe (`LibraryStore.kt:60-64`), and there is no `removeEdit` path.
- Fix: Compare the committed state with the initial/default recipe. If they match, delete the `edits` row, remove the URI from `editedUris`, and invalidate the edited thumbnail.

### LR-QA-005 — Elliptical Lens Blur can rotate differently in preview and export

- Severity: **High**
- Type: Rendering correctness/regression risk
- Evidence:
  - Preview draws Lens Blur before the Compose photo transform, so the ellipse rotates with the displayed photo.
  - Export transforms the bitmap first, then applies Lens Blur.
  - `FrameMap.remap` remaps `lensBlurFocusX/Y` and radius but does not remap `lensBlurAngle` or `lensBlurAspect` (`ImageExporter.kt:228-233`).
- Expected: After 90° rotation or geometry transforms, the Lens Blur ellipse should cover the same pixels in preview and export.
- Actual: Center/radius move, but ellipse orientation/shape remain in the pre-transform coordinate system.
- Fix: Remap two basis vectors for the main and cross axes (as done for mask angles), deriving output angle, main radius, and aspect. Add connected tests combining non-circular blur with 90° rotation, crop, and geometry.

### LR-QA-006 — Subject Lens Blur silently falls back to a hidden geometric focus

- Severity: **Medium**
- Type: Error handling/AI fallback
- Evidence: `ImageExporter.applyLensBlur` sets `useSubject = subjectMask != null`; when segmentation fails, it executes the geometric branch even though the UI still says Person/Face and hides the geometric controls.
- Expected: Skip the effect with feedback, or use a documented fallback the user can control.
- Actual: A stale/default center-radius blur can be applied with no indication that subject detection failed.
- Fix: Return the unblurred bitmap when a requested subject mask is unavailable, surface a non-blocking error, and cover the failure path in tests.

### LR-QA-007 — Important editor controls are unlabeled for accessibility

- Severity: **Medium**
- Type: Accessibility
- Evidence from the UI hierarchy:
  - Exposure, Contrast, Highlights, and Shadows are exposed as SeekBars with empty text/content descriptions.
  - Undo, Redo, Before/After, and Histogram clickable nodes have no meaningful accessibility label.
- Expected: TalkBack should announce the control name, current value/state, and action.
- Actual: Labels are visually adjacent but not associated with the slider semantics; several icon/canvas actions have no accessible name.
- Fix: Add `semantics { contentDescription = ... }`, `stateDescription`, and progress semantics; give undo/redo/compare/histogram explicit descriptions and verify with TalkBack/Accessibility Scanner.

### LR-QA-008 — Corrupt or unsupported imports fail as blank tiles/editors

- Severity: **Medium**
- Type: Error state
- Evidence:
  - The Files picker accepts broad `image/*` and `application/octet-stream` MIME types.
  - `RawDecoder.decode` returns null on every failed decode.
  - `PhotoBitmap` shows a neutral blank box when `bitmap == null` (`MainActivity.kt:566-572`).
  - `EditorScreen` also silently renders no image when its decode is null (`MainActivity.kt:662-665`, `854-855`).
- Expected: Invalid files should be rejected during import or show an actionable “Could not decode this image” state with remove/retry options.
- Actual: Decode failure is visually indistinguishable from indefinite loading.
- Fix: Track loading vs failure explicitly and validate at import time.

### LR-QA-009 — Removing a photo is immediate and leaves album membership behind

- Severity: **Medium**
- Type: Data loss/catalog consistency
- Evidence:
  - “Remove from library” directly invokes deletion without confirmation or undo (`MainActivity.kt:1113-1116`).
  - App-owned fallback copies are deleted immediately (`MainActivity.kt:314-323`).
  - The URI is not removed from the SharedPreferences album sets.
- Expected: Confirm or provide undo, and remove the URI from every album atomically.
- Actual: An accidental tap irreversibly removes the edit recipe/catalog row; stale album URIs remain and may unexpectedly reappear if the same URI is reimported.
- Fix: Add a confirmation dialog or Snackbar undo, and update catalog + albums in one ordered operation.

### LR-QA-010 — Duplicate imports report success even when nothing was added

- Severity: **Low**
- Type: Feedback/catalog UX
- Evidence: `addPhotos` filters duplicates only while adding to `photos`, but its toast uses `added.size`, which still includes duplicates (`MainActivity.kt:222-239`).
- Expected: “Already imported” or an accurate added/skipped count.
- Actual: Re-selecting an existing URI can show “1 photo imported” while the library count does not change.
- Fix: Build an `actuallyAdded` list first and base persistence/toast text on that list.

### LR-QA-011 — Lint cannot pass in the current checkout

- Severity: **Medium (CI/developer workflow)**
- Type: Build quality gate
- Evidence: `local.properties:1` uses `sdk.dir=C:\\Users\\...`; Lint requires the drive colon to be escaped as `C\:\\Users\\...` (or a forward-slash path).
- Expected: `lintDebug` passes or reports only accepted/baselined warnings.
- Actual: 1 error aborts the task. Other notable warnings include platform `android.media.ExifInterface` usage, obsolete target API, missing monochrome launcher icons, and a 16 KB native-library warning.
- Fix: Correct the local property, keep it machine-local, and make lint a CI check. Replace platform EXIF parsing with AndroidX ExifInterface because Android Lint flags known security defects in older platform implementations.

### LR-QA-012 — No automated coverage for the newest Lens Blur and ellipse-mask behaviors

- Severity: **Medium (test gap)**
- Type: Regression coverage
- Evidence: Existing connected tests cover circular Lens Blur and earlier masks, but no test references `lensBlurAspect`, `lensBlurAngle`, `lensBlurSubject`, `lensBlurInvert`, radial-mask aspect, or radial-mask rotation.
- Fix: Add serialization round-trip tests plus preview/export parity tests for ellipse shape, rotation, subject/face focus, invert, segmentation failure, crop, 90° rotation, and geometry.

### LR-QA-013 — Vignette and Optics shading preview do not match export

- Severity: **Medium**
- Type: Rendering correctness
- Reproduction:
  1. Import a flat, evenly lit image.
  2. Apply a strong Post-crop Vignette and change its midpoint, feather, and roundness; also test Optics Vignette separately.
  3. Export at the original aspect and compare the corner/edge falloff with the editor.
- Evidence:
  - `renderKey()` removes `vignette` and `opticsVignette` from the bitmap preview (`MainActivity.kt:1939-1945`).
  - The editor substitutes one radial-gradient overlay and combines the two settings as `vignette + opticsVignette * .5` (`MainActivity.kt:1922-1936`).
  - Export uses different per-pixel vignette/lens-shading equations, aspect/roundness handling, and effect ordering (`ColorEngine.kt:215-226`).
- Expected: The edge falloff shown by the editor should be the same as the saved file.
- Actual: The editor approximation cannot reproduce both export effects or all vignette parameters exactly.
- Fix: Render the same frame-effect algorithm against the visible post-crop frame in both paths, or share a single shader/bitmap implementation. Add pixel-level preview/export tests with non-default midpoint, feather, roundness, crop, and Optics shading.

### LR-QA-014 — Platform EXIF parser is flagged for known security defects

- Severity: **Medium**
- Type: Security/robustness
- Reproduction: Run `gradlew lintDebug` and inspect the `android.media.ExifInterface` warning for `MainActivity.kt:373-374`.
- Expected: Untrusted photo metadata should be parsed by a maintained library compatible with the app's minimum Android version.
- Actual: The import-name path uses the platform EXIF implementation, which Android Lint explicitly warns has known security defects in older implementations.
- Fix: Add current AndroidX ExifInterface, replace the platform import, and test malformed/truncated EXIF payloads.

### LR-QA-015 — Missing monochrome launcher icon

- Severity: **Low**
- Type: Platform UI/polish
- Reproduction: Enable themed icons on Android 13+ and inspect LumaRoom's launcher presentation; `lintDebug` also reports the missing monochrome layer.
- Expected: The adaptive icon should supply a monochrome layer for system theming.
- Actual: Only standard and round icons are declared.
- Fix: Add a monochrome vector/layer to the adaptive icon XML and verify it in light/dark palettes.

### LR-QA-016 — Existing LaMa model is trusted based only on file existence

- Severity: **Low**
- Type: AI error recovery/integrity
- Reproduction:
  1. Install the optional LaMa model.
  2. Truncate or corrupt the final `lama_dilated.tflite` file (representing interrupted restore/storage corruption).
  3. Restart and use Generative Remove.
- Expected: The model should be revalidated and the UI should show a failed/corrupt state with a retry action.
- Actual: `Inpainter.refresh()` reports Ready whenever the file exists; interpreter failure falls back to classic fill while status can remain Ready, and Download is blocked while Ready.
- Fix: Validate expected size/hash during refresh or before the first map, quarantine/delete an invalid file, set `Status.Failed`, and expose Retry download.

## Recommended fix order

1. Raise compile/target SDK to 36 and make Lint pass.
2. Resolve the backup/privacy contradiction before any public release.
3. Upgrade/verify native dependencies on a 16 KB ARM64 device.
4. Fix Lens Blur transform remapping and add parity tests for all new blur/mask fields.
5. Delete the edit row when undo/reset returns to the original state.
6. Add accessible semantics and explicit decode-failure states.
7. Add safe remove/undo behavior and album cleanup.
8. Correct duplicate-import feedback and add UI-level Compose tests for import, editor, persistence, and export flows.
